Workspace Layout
================

HydroModPy organizes work around a **workspace**. The workspace is the durable
place where project configurations, downloaded or prepared data, simulation
catalogs, and run outputs are stored.

The most useful mental model is:

.. code-block:: text

   workspace = shared working area
   project   = one modelling setup inside that area
   run       = one persisted execution of a workflow
   cache     = reusable input data, not a result
   catalog   = index of what has been run

Why A Workspace Exists
----------------------

HydroModPy workflows produce more than one output file. A run can involve DEM
processing, hydrography loading, mesh generation, solver inputs, solver
outputs, figures, and catalog metadata. Keeping all of that next to a random
TOML file would quickly become unreadable.

The workspace gives HydroModPy one stable place for:

- input-data cache shared by several projects;
- project TOMLs and overlays;
- simulation catalog rows;
- result stores such as Zarr folders;
- figures and reports generated by workflows;
- intermediate artifacts that should remain inspectable.

Canonical Layout
----------------

The exact content grows as workflows run, but the intended shape is:

.. code-block:: text

   <workspace>/
   |-- hydromodpy.duckdb
   |-- data/
   |   |-- cache.duckdb
   |   |-- geology/
   |   |-- hydrography/
   |   |-- hydrometry/
   |   |-- intermittency/
   |   |-- oceanic/
   |   `-- recharge/
   |-- simulations/
   |   |-- <sim_uuid>.zarr/
   |   `-- <another_sim_uuid>.zarr/
   `-- projects/
       |-- my_basin/
       |   |-- project.toml
       |   |-- run_mf6.toml
       |   |-- run_nwt.toml
       |   `-- outputs/
       `-- another_basin/
           `-- project.toml

What each part means:

.. list-table::
   :header-rows: 1
   :widths: 26 34 40

   * - Path
     - Meaning
     - User action
   * - ``hydromodpy.duckdb``
     - Workspace-level simulation catalog.
     - Do not edit manually. Use HydroModPy commands and APIs.
   * - ``data/cache.duckdb``
     - Input-data cache metadata.
     - Safe to delete only when you intentionally want to force data reloads.
   * - ``data/<variable>/``
     - Raw or prepared input files grouped by data family.
     - Useful for checking what was downloaded or reused.
   * - ``simulations/<uuid>.zarr/``
     - Physical result store for one persisted run.
     - Treat as generated output; inspect through HydroModPy readers.
   * - ``projects/<name>/``
     - User-facing project folder.
     - This is where TOML files, local overlays, and project-specific outputs
       should live.
   * - ``projects/<name>/outputs/``
     - Common location for workflow-specific reports or comparison outputs.
     - Use subfolders per workflow or scenario.

Scaffold Example
----------------

Start with a workspace and one project:

.. code-block:: bash

   hmp init ~/hmp_workspace
   hmp new my_basin --workspace ~/hmp_workspace

Typical result:

.. code-block:: text

   ~/hmp_workspace/
   |-- hydromodpy.duckdb
   |-- data/
   |-- simulations/
   `-- projects/
       `-- my_basin/
           `-- project.toml

You can then add overlay TOMLs:

.. code-block:: text

   ~/hmp_workspace/projects/my_basin/
   |-- project.toml
   |-- run_overview.toml
   |-- run_mf6_reference.toml
   |-- run_nwt_reference.toml
   `-- compare_mf6_nwt.toml

Base Config And Overlay Configs
-------------------------------

HydroModPy examples often split configuration into a base TOML and smaller run
TOMLs:

.. code-block:: toml

   base_config = "project.toml"
   workflow = "simulation"

The base file owns stable project choices:

- workspace and paths;
- catchment definition;
- DEM and CRS;
- domain depth model;
- common data sources;
- default flow parameters.

The overlay file owns one scenario:

- workflow type;
- run name;
- time window;
- active solver;
- mesh settings;
- calibrated parameters;
- comparison variants.

This pattern keeps repeated information out of each scenario file.

Workspace Resolution
--------------------

Given a TOML file, HydroModPy resolves the workspace using a strict three-step
logic.

1. Explicit workspace paths in the TOML:

   .. code-block:: toml

      [workspace]
      root = "/path/to/workspace"

2. Environment variable:

   .. code-block:: bash

      export HYDROMODPY_WORKSPACE=/path/to/workspace

3. Scaffolded project layout:

   .. code-block:: text

      <workspace>/
      |-- hydromodpy.duckdb
      |-- data/
      `-- projects/
          `-- my_basin/
              `-- project.toml

If none of these works, HydroModPy raises a workspace error instead of silently
guessing a folder.

Explicit Paths
--------------

For portable examples, use paths relative to the TOML:

.. code-block:: toml

   [workspace]
   project_root = "outputs/vire_mf6_irregular"
   root = "../../"

This means:

- the workspace root is two levels above the TOML;
- the project-specific output root is ``outputs/vire_mf6_irregular`` relative
  to the TOML;
- generated run artifacts still belong to the resolved workspace.

Use absolute paths only when a machine-specific workspace is intentional.

How Workflows Use The Workspace
-------------------------------

Different workflows write different kinds of artifacts.

.. list-table::
   :header-rows: 1
   :widths: 20 40 40

   * - Workflow
     - Reads or reuses
     - Writes
   * - ``overview``
     - DEM, geographic sources, requested data families.
     - Identity-card figures, data cache, station inventories.
   * - ``simulation``
     - Geographic context, data cache, mesh input, solver options.
     - Catalog row, solver outputs, Zarr store, figures.
   * - ``testbed``
     - One base TOML plus method-variant overlays, including mesh or flow
       child-runner sections.
     - Generated child configs, case manifest, metrics CSV, report, and links
       to child artifacts such as mesh QA outputs or simulation runs.
   * - ``calibration``
     - Base simulation config, observations, optimizer settings.
     - Calibration history, objective traces, optional promoted best runs.
   * - ``comparison``
     - One base simulation TOML and child overlays.
     - Generated child TOMLs, metrics CSVs, audit report, comparison figures.
   * - ``batch``
     - Site catalog and recipe config templates.
     - Campaign manifest, reports, child run status.

Illustrated Example: One Project, Several Runs
----------------------------------------------

Suppose you are modelling one basin named ``nancon``:

.. code-block:: text

   hmp_workspace/
   |-- data/
   |   |-- geology/
   |   |-- hydrography/
   |   `-- hydrometry/
   |-- simulations/
   |   |-- 1f3a...zarr/
   |   `-- 8ac2...zarr/
   `-- projects/
       `-- nancon/
           |-- project.toml
           |-- run_overview.toml
           |-- run_transient_nwt.toml
           |-- run_calibration_k.toml
           `-- outputs/
               |-- overview/
               |-- nwt_reference/
               `-- calibration_k/

The project folder tells the story of what you intended to run. The
``simulations`` folder stores physical outputs using internal run identifiers.
The catalog links the two.

Illustrated Example: Comparison Workflow
----------------------------------------

A comparison workflow usually has its own output root:

.. code-block:: text

   examples/projects/09_comparison_workflow/
   |-- compare_dupuit_mf6_bouss.toml
   |-- base_dupuit_shared_mesh.toml
   `-- outputs/
       `-- dupuit_mf6_vs_bouss/
           |-- _generated_configs/
           |   |-- mf6_ref.toml
           |   `-- bouss_candidate.toml
           |-- comparison_manifest.json
           |-- comparison_audit.json
           |-- comparison_audit.md
           |-- observables.csv
           |-- comparison_metrics.csv
           |-- comparison_differences.csv
           |-- comparison_report.md
           `-- comparison_figures/

Read this folder from top to bottom:

1. generated configs show what was actually run;
2. audit files tell whether children stayed comparable;
3. observables and metrics contain the numeric comparison;
4. figures summarize the visual differences.

Illustrated Example: Testbed Workflow
-------------------------------------

A mesh testbed wraps several mesh variants without running a simulation. The
testbed folder is the evidence layer; each case row points to the generated
mesh artifacts for one variant.

.. code-block:: text

   outputs/mesh_resolution_testbed/
   |-- _generated_configs/
   |   |-- coarse.toml
   |   `-- fine.toml
   |-- testbed_plan.json
   |-- testbed_cases.csv
   |-- testbed_metrics.csv
   |-- testbed_manifest.json
   `-- testbed_report.md

Read this folder in the same evidence-first order:

1. generated configs show the exact child variants;
2. cases CSV shows which variants ran and where artifacts landed;
3. metrics CSV carries the extracted robustness indicators;
4. report Markdown gives the compact human summary;
5. child mesh artifacts, when present, are inspected as supporting evidence:
   regional figure, local mesh QA figure, summary JSON, and exchange bundle if
   a solver will consume the mesh.

A flow testbed has the same evidence layer, but each generated child is a
normal simulation config:

.. code-block:: text

   outputs/flow_k_sensitivity/
   |-- _generated_configs/
   |   |-- low_k.toml
   |   `-- high_k.toml
   |-- testbed_plan.json
   |-- testbed_cases.csv
   |-- testbed_metrics.csv
   |-- testbed_manifest.json
   `-- testbed_report.md

The generated TOMLs are self-contained ``workflow = "simulation"`` children.
That keeps the base physical case reusable while making the varied axis
explicit in each child config.

Diagnose Resolution
-------------------

Use ``hmp doctor`` to see which workspace was selected:

.. code-block:: bash

   hmp doctor --toml ~/hmp_workspace/projects/my_basin/project.toml

Typical output:

.. code-block:: text

   OK     workspace            resolved via scaffold
   OK     workspace_root       /home/bb/hmp_workspace
   OK     catalog_path         /home/bb/hmp_workspace/hydromodpy.duckdb
   OK     data_dir             /home/bb/hmp_workspace/data
   OK     simulations_dir      /home/bb/hmp_workspace/simulations

When a TOML cannot be resolved, ``hmp doctor`` reports the same workspace
error that ``hmp run`` would raise.

Common Pitfalls
---------------

.. list-table::
   :header-rows: 1
   :widths: 34 33 33

   * - Symptom
     - Likely cause
     - Fix
   * - Outputs appear next to the TOML unexpectedly.
     - Workspace root or project root is not what you thought.
     - Run ``hmp doctor --toml <file>`` and make ``[workspace]`` explicit.
   * - A run reused old input data.
     - Input data were already cached.
     - Clear the relevant cache intentionally, or change source/date
       parameters.
   * - A comparison folder is hard to interpret.
     - Generated child configs were removed or not inspected first.
     - Keep ``comparison.execution.keep_generated_configs = true`` while
       debugging.
   * - A calibration run produced little output.
     - ``save_runs = "none"``.
     - Use ``save_runs = "best_n"`` when you want full outputs for the best
       candidates.
   * - Mesh artifacts overwrite each other in batch mode.
     - Fixed mesh output names are reused across outlets.
     - Use ``[mesh_catchment_batch.outputs]`` patterns with ``{outlet_id}``.

Practical Rules
---------------

- Keep one workspace per study or teaching session.
- Keep one project folder per basin or modelling setup.
- Use base TOMLs for stable site configuration.
- Use overlay TOMLs for scenarios, solvers, calibration, and comparisons.
- Use ``hmp doctor`` whenever outputs are not where you expected.
- Do not manually edit DuckDB catalogs or Zarr stores.
