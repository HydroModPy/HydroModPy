HTML Report Generation
======================

The ``site_selection`` HTML review page is an end-of-run consumer of completed
selection artifacts. It does not run candidate loading, DEM processing,
delineation, criteria evaluation, or provider access. Those phases must finish
first and declare their outputs in ``site_selection_manifest.json``.

This separation is the main contract to preserve when changing the report: the
HTML page is reproducible from the manifest and the files listed in
``manifest["outputs"]``.

Runtime Trigger
---------------

A site-selection TOML requests the static report through the generic report
intent:

.. code-block:: toml

   [report.html]
   profile = "site_selection"
   build_at_end = true

``hydromodpy.workflow.site_selection.load_site_selection_config`` reads this
section through the shared report loader. When ``build_at_end`` is true, the
workflow validates that the explicit profile is either omitted or equal to
``site_selection``, then stores the request on the workflow-local
``SiteSelectionConfig.report_html_build_at_end`` flag.

Older site-selection-specific switches such as ``write_report_html`` are not
part of the current public contract. Example TOMLs should use ``[report.html]``
so report intent is expressed the same way as other HydroModPy workflows.

Completed Run Flow
------------------

For executed selections, all input modes converge on the same reporting path:

.. code-block:: text

   hmp run config.toml
        |
        +-- build candidates and catchments
        +-- evaluate criteria and decisions
        +-- write CSV / JSONL / GeoJSON outputs
        +-- write site_selection_manifest.json
        +-- render review/site_selection_map.png
        +-- render review/*.html
        +-- write report_artifact_manifest.json

The output assembly is coordinated by
``hydromodpy.spatial.site_selection.outputs.artifacts.write_manifest_and_optional_report``.
That helper writes the official manifest first. If HTML reporting is requested,
it pre-declares these report outputs in the manifest:

- ``site_selection_report_html`` -> ``review/index.html``;
- ``site_selection_map_png`` -> ``review/site_selection_map.png``.

The workflow injects
``hydromodpy.reporting.site_selection.html.render_site_selection_html_report``
as the renderer. This keeps the spatial output helper independent from the
reporting and display stack.

Renderer Responsibilities
-------------------------

``render_site_selection_html_report`` performs the report-only work:

#. load and validate ``site_selection_manifest.json``;
#. skip validation of the report HTML and map PNG, because those files are being
   generated by the renderer;
#. resolve artifact paths through
   ``hydromodpy.schema.site_selection_manifest.manifest_output_path``;
#. read selected/rejected site CSV files;
#. read decision, criteria, evidence, and candidate-audit JSONL files;
#. render the static review map;
#. build site-selection report blocks;
#. write the HTML entry points.

The renderer deliberately reads normalized run artifacts, not provider payloads
or in-memory selection objects. Missing optional artifacts should degrade the
page where possible. Missing required artifacts should be caught by manifest
validation before the page is written.

Map Generation
--------------

The review map is generated before the HTML pages and then used as a report
figure. ``hydromodpy.reporting.site_selection.figures.render_site_selection_map``
reads only manifest-declared spatial artifacts:

- selected and rejected basin GeoJSON files;
- selected and rejected outlet GeoJSON files;
- observation points;
- DEM network layers when the DEM candidate modes produced them;
- configured map-context layers;
- the DEM background selected by the manifest.

The map is written to ``review/site_selection_map.png``. Report blocks reference
that PNG as the ``site_selection_map`` figure. When the PNG is small enough, the
shared block renderer embeds it directly in the HTML as a ``data:image/png``
URI, which keeps ``review/index.html`` easy to open locally without a web
server.

HTML Pages
----------

The static block renderer writes four entry points:

.. list-table::
   :header-rows: 1
   :widths: 28 72

   * - Page
     - Purpose
   * - ``review/index.html``
     - Main review page with per-block detail controls.
   * - ``review/compact/index.html``
     - Short plausibility review.
   * - ``review/standard/index.html``
     - Default scientific review depth.
   * - ``review/audit/index.html``
     - Detailed provenance, evidence, and artifact links.

The page content is built from ``ReportBlock`` objects in
``hydromodpy.reporting.site_selection.blocks``. Workflow-specific code decides
which blocks exist and what they mean. The shared renderer in
``hydromodpy.display.report_blocks.html`` is responsible only for generic HTML:
metrics, tables, figures, links, warnings, navigation, and detail-level
switching.

Report Artifact Manifest
------------------------

After the HTML renderer returns, the workflow writes
``report_artifact_manifest.json``. This file is a generic artifact index built
from the outputs declared by ``site_selection_manifest.json``.

Use the two manifests for different jobs:

.. list-table::
   :header-rows: 1
   :widths: 34 66

   * - File
     - Use it for
   * - ``site_selection_manifest.json``
     - Domain semantics: run action, territory, strategy, criteria, counts,
       DEM settings, and output artifact ids.
   * - ``report_artifact_manifest.json``
     - Generic frontend integration: artifact status, kind, producer, labels,
       metadata, and links.

Downstream frontends should prefer the site-selection manifest when they need
selection meaning, and the report-artifact manifest when they need a generic
file list.

Plan-Only Reports
-----------------

The ``plan`` or ``dry_run`` action uses the same ``[report.html]`` trigger but a
different renderer:
``hydromodpy.reporting.site_selection.plan.render_site_selection_plan_html_report``.
It reads ``site_selection_plan.json`` instead of a completed selection manifest
and writes the same page layout under ``review/``.

Plan reports are useful for checking resolved configuration, planned outputs,
territory settings, DEM intent, and reporting switches before provider loading
or DEM processing is allowed to run.

Implementation Checklist
------------------------

When changing site-selection HTML reporting, check these points before relying
on the generated page:

- the source data for a new block is written as CSV, JSONL, GeoJSON, or another
  declared artifact before rendering starts;
- the artifact has a stable output key in ``site_selection_manifest.json``;
- ``report_artifact_manifest.json`` classifies the artifact with a useful kind,
  producer, and metadata;
- the renderer resolves the artifact path through the manifest helper instead
  of hard-coding filenames;
- the report block consumes normalized artifacts and does not call provider,
  DEM, delineation, or criteria code;
- the page still writes ``review/index.html``, ``review/compact/index.html``,
  ``review/standard/index.html`` and ``review/audit/index.html``.

Regeneration
------------

Because the completed report is manifest-driven, a report can be regenerated
from an existing run by calling the renderer with the selection manifest path:

.. code-block:: python

   from hydromodpy.reporting.site_selection.html import (
       render_site_selection_html_report,
   )

   render_site_selection_html_report(
       "outputs/my_selection/site_selection_manifest.json"
   )

This should rebuild the map and HTML pages without changing selection
decisions. If regeneration would require re-running candidate loading,
delineation, or criteria evaluation, the report contract has been broken.
