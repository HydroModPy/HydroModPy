# model

The model is what a groundwater solver reads, written without any solver. A `[domain]` table says where the aquifer lies, a `[flow]` table gives its parameters, initial heads, boundaries and sinks and sources, and a `[transport]` table holds the tracking settings. The package turns those tables into typed config models and the config models into runtime objects. It puts the forcings on the cells of a mesh, maps the properties onto those cells, binds loaded data to the flow and holds the arithmetic of the daily soil reservoir that turns the weather into recharge. `Flow` (`flow.py`) is the object the setup binds loaded data to, `Model` (`model.py`) is the frozen object a solver reads, and `prepare_solver` builds it from the `Flow`. The package is a layer because the solvers, the workflow, the calibration and the results all need one description of the model, and none of them should own it.

The model reads `core`, `schema`, `catchment` and `mesh`, and never `data`, `results` or `solver`. It sees loaded data through the two protocols of `contracts.py`. It is read by `solver` (most of it), `workflow`, `calibration`, `config`, `data`, `results`, `project` and the package root. The order of the layers is in `tests/unit/architecture/layer_matrix.yaml`.

The package has nine folders: `domain/`, `properties/`, `forcing/`, `boundaries/`, `sinks_sources/`, `initial/`, `time/`, `soil/` and `transport/`. The folder `boundaries/` is a port and has its own README, which names the boundary ids a solver backend can serve. The page of the package lists every module with the first line of its docstring, and it says how a flow is built and where to add what.
